# Начальное число воркеров с сохранением автоматики

```bash
./overviewer.py --config=./configNew.py --start-workers=6 --cpu-limit=10 --memory-limit=13G
```

После подготовки текстур/плана координатора запускаются сразу 6 процессов.
Они загружают общий приватный снимок исходных данных и готовят текстуры параллельно.
Обработка тайлов начинается, как только готов первый процесс. Остальные продолжают
инициализацию. Предел CPU относится ко всей группе и не резервирует ядра от других программ.

- `--start-workers=6`: сколько процессов подготовить в начальном пуле.
- `--cpu-limit=10`: максимум доступных логических CPU.
- `-p=8`: необязательный максимум воркеров, здесь 8 при доступных 10 CPU.
- `--memory-limit=13G`: суммарный жёсткий бюджет cgroup, включая данные, процессы и кэш.

Чтобы стартовать с 6 и не добавлять больше 6:

```bash
./overviewer.py --config=./configNew.py --start-workers=6 -p=6 --cpu-limit=10 --memory-limit=13G
```

Без --start-workers начальный пул по-прежнему начинается с одного процесса и
постепенно растёт. Сохранённый профиль ускоряет набор. Явный стартовый размер
должен быть положительным и не превышать максимум CPU/-p. При известных меньших
безопасных пределах профиля или OOM-повтора фактический стартовый пул уменьшается.
Начальный размер не включён в ключ профиля/тайлов: менять этот параметр между
запусками одной версии можно без сброса плана.

Начальные 6 — запрос, а не гарантия их размещения. Одновременная инициализация
может дать пик RAM и вызвать OOM, если оценка была слишком оптимистичной.
Контроллер остаётся вне cgroup, уменьшает максимум и повторяет сохранённый план.
Например, при старте 6 и OOM предел станет 3: повтор с тем же --start-workers=6
начнёт с трёх, а не снова с шести. После запуска динамический подбор сохраняется.

Параметр несовместим с `--fixed-resources` и `--genpoi`. Для запуска исходников
нужен конечный проверенный memory cgroup: обычно указывают --memory-limit.

## Установка на незавершённый рендер прежней сборки

Скачайте отдельный `fix_start_workers.py` из Assets выпуска .12 и положите
в существующую папку CublayCraft-Overviewer. После Ctrl+C и выхода рендера:

```bash
cd /media/disk/overviewer/CublayCraft-Overviewer
./runtime/bin/python3 ./fix_start_workers.py .
./overviewer.py --config=./configNew.py --start-workers=6 --cpu-limit=10 --memory-limit=13G
```

Патч рассчитан на адаптивные сборки resume.6–resume.11. Он добавляет два модуля
рядом с app/overviewer.py и подключение в точку входа. Включено и исправление
файлового кэша, если оно ещё не было установлено. Core не меняется; его контрольная
сумма проверяется до/после. Совместимый журнал продолжит оставшиеся тайлы.
Повторная установка допустима; исходная точка входа сохраняется в
`app/overviewer.py.before-start-workers.bak`. Приветствие сохраняет прежнюю версию.

Ожидаемые строки: `Initial worker pool enabled`, `Initial pool: requested=6,
starting=6` и `Resuming ... skipping chunk/tile scan`. Подготовка текстур
координатора выполняется снова. Для продолжения используйте прежний config/output
без --forcerender и --discard-resume. Полное обновление core старой сборки может
сделать прежний план несовместимым, поэтому для незавершённого плана нужен патч.

## Проверка

- Настоящий рендер 26.3: все шесть процессов начали инициализацию в одну секунду,
  401 задача завершена под лимитом 4 GiB; JSON фиксирует requested=6, started=6.
- Под лимитом 1 GiB старт шести получил kernel OOM. Повтор начал с трёх,
  продолжил сохранённый план без сканирования; автоматика вывела ещё один
  процесс и завершила работу двумя. CLI всё время содержал --start-workers=6.
- Установка патча на прежний core сохранила ключ реального журнала; продолжены
  353 оставшихся тайла тремя процессами без сканирования мира.
- Проверены параллельная загрузка, очистка приватного снимка, пустой план,
  сохранённый безопасный максимум и ошибки недопустимых параметров.

Снимок хранится в приватном временном каталоге, а не в веб-каталоге карты.
При штатном завершении/прерывании удаляется. В managed-сессии он размещается
в приватном каталоге контроллера и очищается также при завершении OOM-повторов.
В `render-resources.json` поля initial_workers_requested/initial_workers_started
находятся внутри отдельных attempts.
