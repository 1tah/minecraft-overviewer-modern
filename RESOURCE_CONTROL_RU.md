# Автоматическое управление CPU и RAM

Для готового архива Ubuntu 20.04 x86_64:

```bash
./overviewer.py --config=./configNew.py --cpu-limit=12 --memory-limit=10G
```

Для исходников в современной Ubuntu/WSL с рабочей systemd user session:

```bash
.venv/bin/python overviewer.py -c ./configNew.py --cpu-limit=12 --memory-limit=10G
```

`--cpu-limit` задаёт максимум **логических CPU** через Linux affinity всей группы.
У Ryzen 5700X их 16. Ограничение 12 разрешает выполнение на выбранных 12 CPU;
это не резервирование CPU от других программ и не процентная квота загрузки.
По возможности сначала выбираются разные физические ядра, затем SMT-потоки.
Численные библиотеки в рабочих процессах ограничены одним внутренним потоком.

`-p N` в авто-режиме задаёт максимум **рабочих процессов**. Если одновременно
заданы `--cpu-limit=12 -p=8`, максимум работников равен 8, разрешены 12 CPU.
`--start-workers=6` задаёт начальный пул из шести процессов, инициализируемых
параллельно после подготовки координатора. Автоматика сохраняется; при OOM-повторе
или меньшем безопасном пределе профиля начальный пул сокращается.
Например: `--start-workers=6 --cpu-limit=10 --memory-limit=13G`.
Подробности и патч для незавершённого плана: [START_WORKERS_RU.md](START_WORKERS_RU.md).
Если -p отсутствует, максимум работников равен количеству разрешённых CPU.
В готовом архиве авто-режим включён по умолчанию. В исходниках его включает
`--memory-limit` или явный `--auto-resources` внутри уже ограниченной cgroup.
Старая настройка `processes` в конфиге используется фиксированным режимом;
в авто-режиме верхнюю границу задают ключи запуска.

RAM — общий жёсткий бюджет cgroup: координатор, текстуры, рабочие процессы,
вспомогательные процессы и память, учитываемая ядром в группе. Это не обещание
занять весь бюджет. Дополнительные процессы могут не ускорять рендер из-за
диска, зависимостей обзорных тайлов или SMT. На современном cgroup v2 swap
группы отключён; в v1 возможности ограничения swap зависят от ядра.

## Как работает подбор

1. Подготовка и сканирование выполняются до запуска пула. По умолчанию пул начинает
   с одного работника. Явный --start-workers создаёт начальный пул параллельно;
   последующий автоматический рост инициализирует максимум один новый процесс за раз.
2. Примерно раз в секунду контроллер читает расход всей cgroup и RSS работников.
   Для подбора используется расход за вычетом потенциально освобождаемого
   неактивного файлового кэша. Вычитается не больше `inactive_file` и объёма
   файлового кэша за вычетом shmem, грязных страниц и страниц в записи.
   Активный файловый кэш, анонимная память и slab остаются в рабочем бюджете.
   В cgroup v1 используются иерархические `total_*`, если они доступны.
   При недоступной/неправильной статистике вычета нет.
   Он добавляет процесс только при запасе RAM, с консервативной оценкой стоимости
   следующего процесса и резервом. Между добавлениями есть пауза.
3. При рабочем расходе около 82% лимита один работник выводится из пула: завершает
   текущий тайл и выходит. При освобождении памяти пул снова может вырасти.
   В каждый процесс отправляется максимум одна задача одновременно.
4. Резкое выделение памяти всё равно может вызвать kernel OOM. Внешний контроллер
   остаётся вне ограниченной группы, уменьшает максимум работников примерно
   вдвое и запускает ту же задачу по SQLite-журналу. Подтверждённые тайлы остаются;
   незавершённые и последние незафиксированные тайлы могут повториться.
5. Если не помещается подготовка или один работник, автоматические повторы
   прекращаются. Увеличьте лимит либо уменьшите набор слоёв/объём текстур.

Нельзя гарантировать отсутствие любого OOM при произвольных мирах. Автоматика
снижает риск и восстанавливает работу после OOM, когда меньший пул помещается.
Начальный анализ до создания журнала может потребовать повторения. Обычные ошибки
конфига, повреждённые чанки и Ctrl+C не запускают цикл автоматических повторов.

## Результат и следующий запуск

В автоматическом режиме консоль использует строки журнала, чтобы сообщения
изменения пула не смешивались с интерактивной полосой. Вывод содержит число
тайлов, проценты до сотых, TPS и ETA. `--simple-output` и старое сокращение
`--simple` тоже выбирают этот режим. В фиксированном режиме с обычным TTY
интерактивная полоса остаётся доступной. Веб-полоса работает независимо.
Для старой установки достаточно добавить `--simple` при следующем плановом запуске.

Веб-статус во время рендера показывает `RAM 3.3/10.0 ГиБ · Воркеры 4/12`:
компактный блок шириной до 500 px содержит слой и прогресс в первой строке,
остаток, ETA и ресурсы — во второй. При узком экране текст переносится.
До часа ETA имеет вид `Осталось ~37 мин`, от часа — `Осталось ~02:15`.
Часы обозначают длительность и не сбрасываются после 24. Полная расшифровка
статуса доступна при наведении; `(+1)` обозначает инициализацию одного воркера.
RAM — расход всей ограниченной cgroup и её предел, затем число готовых рабочих
процессов и максимум пула. Временно простаивающие готовые процессы тоже входят
в число воркеров. Инициализация обозначается `(+1)`, в полной расшифровке — `(запуск 1)`.
Основной индикатор RAM включает файловый кэш, поэтому может оставаться близким
к лимиту даже при возможности увеличить пул: ядро освобождает чистые файловые
страницы по мере необходимости. В новой сборке наведение показывает отдельно
рабочую память и потенциально освобождаемый кэш; жёсткий лимит применяется к сумме.
Значения обновляются примерно раз в две секунды независимо от завершения тайлов.
После завершения показано «Рендер завершён», «13 634 из 13 634 тайлов · 100%»,
время рендера (от начала пула, включая инициализацию), пик RAM и максимум готовых
воркеров попытки. Это общий итог всех слоёв; подготовка текстур до пула в это время
не входит. После остановки текущие ресурсы скрыты, показывается пик RAM попытки.
Если heartbeat пропал, старые показания ресурсов скрываются, а строка сообщает
об отсутствии обновлений. В запуске без доступной ограниченной cgroup расход RAM
не выводится; количество воркеров доступно и для фиксированного режима.

В конце консоль показывает использованные логические CPU, минимум/максимум/среднее
число работников, пик RAM, среднюю скорость и рекомендуемый размер пула.
`output/render-resources.json` содержит также отдельные попытки, изменения пула,
общее время и количество OOM-повторов. Пик RAM в нативной сборке берётся из ядра;
при запуске исходников используется также доступная статистика systemd.
Среднее число работников считается по времени существования готового пула;
`average_busy_workers` отдельно отражает занятых задачами работников. Время
инициализации входит в длительность рендера, поэтому среднее может быть меньше 1.
Скорость рендера и скорость за полное время запуска отличаются из-за подготовки.

`output/.overviewer-autotune.json` хранит рекомендацию и выученный безопасный
максимум. При следующем запуске рост к рекомендованному числу происходит быстрее,
но процессы всё равно добавляются постепенно с проверкой RAM. Профиль учитывает
конфигурацию рендера, бюджет RAM, число CPU и архитектуру. После изменения бюджета
или рендера подбор начинается заново. Короткий рендер даёт предварительную оценку:
на нём может не хватить времени, чтобы сравнить скорости разных размеров пула.
Для сброса подбора можно удалить только `.overviewer-autotune.json`.

## Привычный фиксированный режим

```bash
./overviewer.py --config=./configNew.py --fixed-resources -p=6 --cpu-limit=8 --memory-limit=10G
```

Здесь процессов ровно 6, автоматического изменения и OOM-повторов нет, жёсткий
лимит RAM сохраняется. Генерация маркеров `--genpoi` тоже использует прежний пул.

При обновлении с предыдущего выпуска состав исходников меняет ключ совместимости
журнала. Поэтому незавершённый план старой версии может потребовать нового анализа.
Внутренние OOM-повторы одного выпуска используют совместимый план без полного сканирования.
